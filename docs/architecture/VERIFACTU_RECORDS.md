# VeriFactu Records

This document defines the first persistence boundary for MetalWolft's future
VERI*FACTU integration.

## Scope

This phase creates an auditable, deterministic record of the fiscal content that
will later be serialized and transmitted to AEAT.

It does not implement:

- HTTP transmission to AEAT.
- XML official serialization.
- Certificate signing.
- QR generation.
- Cancellation records.
- Retry automation.

## Domain Boundary

The current flow is:

```text
Issued Invoice
    -> immutable InvoiceSnapshot v1
    -> persisted VeriFactu registration record
    -> future official serialization
    -> future AEAT submission
    -> future AEAT response
```

`VeriFactuRecord` is not:

- the invoice;
- the invoice PDF;
- the accounting entry;
- the AEAT sales ledger Excel;
- a submission attempt.

Submission attempts continue to belong to `InvoiceFiscalSubmission`.

## Hashes

`Invoices.invoice_snapshot_hash` is an internal integrity hash. It proves that
the stored `invoice_snapshot` has not changed inside MetalWolft.

It is not the official VeriFactu fingerprint.

`VeriFactuRecord.record_payload_hash` is also internal. It proves that the
persisted VeriFactu record payload has not changed.

The official VeriFactu fingerprint remains `NULL` until it can be implemented
exactly according to the official specification with reliable vectors.

For records prepared in the local `READY` phase, the fingerprint is calculated
only for the supported `RegistroAlta` subset and persisted together with the
exact input string. This local state still does not mean submitted, accepted or
validated by AEAT.

## READY State

`READY` means:

- `OfficialRegistrationData` has been derived from the immutable invoice
  snapshot.
- The exact fingerprint input string has been persisted.
- The SHA-256 fingerprint has been calculated and persisted.
- The local chain points to the previous `READY` record for the same system
  installation, or marks the record as first.
- The logical official payload has been persisted for future serialization.

`READY` does not mean:

- sent;
- accepted;
- presented;
- transmitted;
- signed;
- included in a QR;
- validated by AEAT.

## Official Fingerprint Input

The fingerprint input is not built from JSON, the internal payload hash, the
invoice snapshot hash, a Python `repr()` or provisional XML.

For `RegistroAlta`, the stored string follows this order:

```text
IDEmisorFactura=<issuer tax id>&
NumSerieFactura=<invoice number>&
FechaExpedicionFactura=<DD-MM-YYYY>&
TipoFactura=F1&
CuotaTotal=<tax amount with 2 decimals>&
ImporteTotal=<total amount with 2 decimals>&
Huella=<previous fingerprint or empty>&
FechaHoraHusoGenRegistro=<ISO datetime with timezone>
```

Only ordinary invoices are currently mapped to `TipoFactura=F1`.

## Chain

The official rule distinguishes a chain by taxpayer and information system.
MetalWolft represents that in the local persistence layer with this internal
key:

```text
chain_key =
  issuer_tax_id |
  mode |
  producer_tax_id |
  system_id |
  installation_id
```

Rationale:

- `issuer_tax_id` represents the taxpayer obliged to issue the invoice.
- `mode` distinguishes the VERI*FACTU mode stored in the record.
- `producer_tax_id`, `system_id` and `installation_id` identify the information
  system installation that generates the records.
- `system_version` is persisted in the record but is not part of the key, so a
  normal software upgrade does not split the legal chain.

The chain order is not inferred from `id DESC`, `created_at DESC` or
`SELECT MAX(...)`.

Each prepared record stores:

- `chain_key`;
- `chain_sequence`;
- `previous_record_id`;
- `previous_fingerprint`;
- `is_first_record`.

`VeriFactuChainState` stores the current head of each chain:

- `chain_key`;
- `last_record_id`;
- `last_fingerprint`;
- `next_sequence`.

During preparation, the service obtains the chain state row with
`SELECT FOR UPDATE`, reads the current head, assigns `chain_sequence`, calculates
the fingerprint with the previous fingerprint from the locked head, updates the
record, and advances the head in the same transaction.

If no head exists, the service creates the chain state and assigns sequence 1.
That record is marked `is_first_record=True` and the previous fingerprint segment
is empty.

If a record is already `READY`, preparation returns it without acquiring a new
position, without incrementing the sequence and without moving the chain head.

If the transaction rolls back before commit, neither the record nor the chain
head advance. The service does not perform commit or rollback internally.

SQLite tests validate the logical sequence, constraints and idempotency, but
SQLite does not prove `SELECT FOR UPDATE` locking behavior. PostgreSQL validation
is required before production activation.

Constraints protect against local bifurcation:

- unique `(chain_key, chain_sequence)`;
- unique `previous_record_id` for direct children;
- `previous_record_id != id`;
- `READY` records must have `chain_key`, `chain_sequence` and `fingerprint`;
- first records must have no previous record and sequence 1;
- following records must have a previous record and sequence greater than 1.

A correct individual fingerprint does not prove a safe chain. Chain safety
requires the locked head row, persisted sequence and database constraints.

This is local preparation only. The final legal chain requirements must still be
verified against the complete official XML and submission rules before
production transmission.

## System Identity

The constructor requires explicit system identity:

- `system_id`
- `system_name`
- `system_version`
- `installation_id`
- `producer_name`
- `producer_tax_id`

These values are persisted inside the record payload. They must later come from
approved configuration, not from the browser.

Runtime configuration keys:

- `VERIFACTU_ENABLED=false`
- `VERIFACTU_SYSTEM_NAME`
- `VERIFACTU_SYSTEM_VERSION`
- `VERIFACTU_SYSTEM_ID`
- `VERIFACTU_INSTALLATION_ID`
- `VERIFACTU_PRODUCER_NAME`
- `VERIFACTU_PRODUCER_TAX_ID`

`VERIFACTU_ENABLED` remains disabled by default and does not trigger submission
or automatic behavior in this block.

## Idempotency

The registration record is unique by:

```text
(invoice_id, record_type)
```

For v1, only `record_type="alta"` is built.

Calling the constructor again for the same invoice and record type returns the
existing record and does not rebuild a different payload.

## Current Blockers For Real Transmission

P1 for transmission, not for persistence:

- official XML structure;
- complete XML/schema validation for all supported record types;
- PostgreSQL concurrency validation before production activation;
- certificate/signature requirements;
- QR content requirements;
- registration and cancellation final schemas;
- AEAT response mapping.

Until those are closed, the system must not transmit this payload as if it were
the official AEAT message.
